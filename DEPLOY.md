# Развёртывание на сервере

Всё ниже выполняется **на сервере, где крутится pm2** (тот же, что у Listings),
под пользователем `parsemgr`, **в RDP-сессии этого пользователя** — не на ноутбуке.

Два требования, из которых всё вытекает:

- **Chrome нужен для куки `cf_clearance`** (шаг 6), а не для работы: получив куку,
  краулер ходит обычным HTTP. Кука лежит в `data/clearance.json` и переживает
  перезапуски. НО Cloudflare отзывает её и раньше заявленного года (наблюдали через
  ~40 минут после большого прогона), и тогда краулер поднимает Chrome сам. Значит
  **процессу нужна живая сессия пользователя постоянно**, а не только при установке:
  headless Cloudflare режет. Сколько раз клиренс обновлялся за прогон, видно в логе
  и в `scrape_runs.note` — если окажется, что это редкость, требование можно ослабить.
- **База видна только из сети сервера.** С ноутбука `172.30.0.185:5432` недоступен,
  поэтому миграция и первый запуск — с сервера.

## Шаг 0. Проверить, что на сервере есть всё нужное

```powershell
node -v                                              # нужен Node 18+
Test-Path 'C:\Program Files\Google\Chrome\Application\chrome.exe'
```

Если `False` — найти реальный путь и позже прописать его в `.env` (`CHROME_PATH`):

```powershell
Get-ChildItem 'C:\Program Files\Google\Chrome\Application\chrome.exe',
              'C:\Program Files (x86)\Google\Chrome\Application\chrome.exe',
              "$env:LOCALAPPDATA\Google\Chrome\Application\chrome.exe" -ErrorAction SilentlyContinue |
  Select-Object FullName
(Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\chrome.exe' -ErrorAction SilentlyContinue).'(default)'
```

Не нашёлся — поставить: `winget install --id Google.Chrome -e`. Chrome нужен только для
шага 6 (одна кука), в работе краулера он не участвует.

Порты `9333`, `9334`, `9335` должны быть свободны:

```powershell
Get-NetTCPConnection -LocalPort 9333,9334,9335 -ErrorAction SilentlyContinue
```

Пусто — значит свободны.

## Шаг 1. Скопировать проект

Рядом с Listings, например `C:\Users\parsemgr\Downloads\linkedin-agent\.git\refs\Scrapper\`.

Весь проект без `node_modules` — меньше мегабайта. Копировать **всё, кроме**:

```
node_modules\         зависимости (10 МБ) — поставятся на сервере
data\dry-run\         результаты локальной проверки
data\*.log
data\clearance.json   куку получим на сервере: она привязана к IP
.cf-profile*\         временные профили Chrome, если остались
```

`.env` скопировать обязательно (или создать из `.env.example`).

Одной командой с ноутбука:

```powershell
robocopy '<локальная папка Scrapper>' 'C:\Users\parsemgr\Downloads\linkedin-agent\.git\refs\Scrapper' `
         /E /XD node_modules dry-run .cf-profile .cf-profile-scrape .cf-profile-status .cf-profile-tools `
         /XF clearance.json dryrun-full.log dryrun-http.log
```

После копирования проверить, что доехали ключевые файлы:

```powershell
Test-Path .env, data\brands.json, lib\session.js    # должно быть три True
```

## Шаг 4. Накатить миграции (под владельцем схемы)

`CREATE SCHEMA` и `GRANT` требуют прав владельца, `lo_agent` их не имеет — нужен пароль
`lo_admin` (тот же, которым создавалась схема `listings`).

Файлы из `migrations/` выполняются **вручную**, по порядку номеров:

| Файл | Что делает |
| --- | --- |
| `001_scrapper_schema.sql` | схема, 4 таблицы, представления, GRANT'ы для `lo_agent` |
| `002_deal_alerts.sql` | таблица отправленных уведомлений (без неё бот шумит повторами) |
| `003_alert_outcomes.sql` | вьюха исходов рекомендаций |
| `004_seller_paused.sql` | причина «пауза кабинета» + разовая переразметка накопленного |

Каждый файл начинается комментарием о том, что он делает и почему. Все идемпотентны:
повторное применение безопасно, а `001` при непустой таблице `listings` намеренно падает
с сообщением, вместо того чтобы снести данные.

Проверить результат после применения:

```powershell
npm run db-check
```

Файл пересоздаёт схему с нуля, но в начале стоит защита: если в `scrapper.listings`
уже есть строки, миграция падает с сообщением вместо того, чтобы снести данные.
Менять схему на живых данных нужно отдельным файлом `002_*.sql`.

## Шаг 5. Проверить базу под рабочим пользователем

```powershell
npm run db-check
```

Ожидаемо: `ИТОГ: база готова`. Что означают ошибки:

- `схемы scrapper нет` — шаг 4 не выполнен или выполнен в другую базу;
- `ОШИБКА записи` — не выданы GRANT'ы: выполнить блок GRANT из конца
  `migrations/001_scrapper_schema.sql` под `lo_admin`;
- `база видна только из сети сервера` — вы не на сервере.

## Шаг 6. Получить куку Cloudflare (единственный шаг, которому нужен Chrome)

Выполнять **в RDP-сессии пользователя**, руками, один раз:

```powershell
npm run clearance
```

Что происходит: поднимается Chrome с окном за пределами экрана, сам решает челлендж,
из него забирается `cf_clearance`, Chrome гасится, профиль удаляется. Кука сохраняется
в `data/clearance.json`.

Ожидаемый вывод:

```
[clearance] получен, действует до 2027-...
  Chrome поднимался в этот раз: да
проверяю боем... ок: 264800 байт, карточек 20, за ~1800 мс
ИТОГ: доступ к сайту есть, браузер для работы краулера не нужен
```

Повторный запуск `npm run clearance` уже не поднимает Chrome — берёт куку с диска.
Принудительно обновить: `node tools/clearance.js --refresh`.

**Если не получилось:**

| Симптом | Причина и что делать |
| --- | --- |
| `Chrome не найден: ...` | не тот `CHROME_PATH` в `.env` (шаг 0) |
| `cf_clearance не выдан` и дальше «страница настоящая — Cloudflare челлендж не показал» | норма: этому IP Cloudflare проверку не показывает, кука не нужна. Если «проверяю боем... ок» — всё работает |
| `cf_clearance не выдан, и это не страница bamper.by` | смотреть строку «Вкладка: ... title: ... текст: ...» выше в логе: там видно, что открыл Chrome. «Access denied» — IP заблокирован сайтом |
| `Chrome не открыл порт отладки 9333` | процессу недоступен рабочий стол — запускать из RDP-сессии, не из службы |
| `челлендж не пройден` три раза | увеличить `CF_SOLVE_WAIT_MS` до 25000-30000; проверить, открывается ли bamper.by в обычном браузере на этом сервере |
| хочется посмотреть глазами | `$env:CHROME_VISIBLE='true'; node tools/clearance.js --refresh` — окно будет видно |

После этого шага краулер работает по HTTP и поднимает Chrome сам, только когда
Cloudflare отзовёт куку. Проверить, часто ли это происходит:

```sql
SELECT started_at, mode, note FROM scrapper.scrape_runs ORDER BY id DESC LIMIT 20;
```

## Шаг 8. Поставить задачи в расписание (pm2)

Каждый режим — отдельный файл в `jobs/`, аргументы командной строки не нужны:

```powershell
pm2 start jobs/incremental.js --name bamper-incremental --no-autorestart --kill-timeout 30000 --cron "5,35 * * * *"
pm2 start jobs/full.js        --name bamper-full        --no-autorestart --kill-timeout 30000 --cron "0 3 * * *"
pm2 start jobs/notify.js      --name bamper-notify      --no-autorestart --kill-timeout 30000 --cron "10,40 * * * *"
pm2 start check-status.js     --name bamper-status      --no-autorestart --cron "0 9 * * *"
pm2 save
pm2 list
```

Команды по одной строке каждая — не склеивайте их переносами, иначе PowerShell уйдёт
в режим продолжения (приглашение `>>`) и всё попадёт в один вызов pm2.

**Почему отдельные файлы, а не `-- full`.** pm2 на Windows принимает аргументы после
`--` за имена скриптов: в логе это выглядит как
`[PM2][ERROR] Script not found: ...Scrapperull`, при этом сама задача создаётся,
но запускает `scrape.js` без режима — то есть тихо работает как `incremental`.
Файлы в `jobs/` эту ловушку убирают. Режим можно задать и переменной `SCRAPE_MODE`.

| Задача | Когда | Что делает | Сколько идёт |
| --- | --- | --- | --- |
| `bamper-incremental` | в :05 и :35 каждого часа | первые 3 страницы свежих по каждой марке: новые объявления и смены цены, плюс добор 60 страниц объявлений | ~4 минуты |
| `bamper-full` | ежедневно в 03:00 | все страницы всех марок, пометка ушедших, добор 300 страниц объявлений | ~25 минут |
| `bamper-status` | ежедневно в 09:00 | сводка за сутки + проверка ушедших по прямой ссылке | ~2 минуты |

Учтите: `pm2 start` запускает задачу сразу, не дожидаясь крона.

`--kill-timeout 30000` нужен, чтобы прогон успел закрыться по-человечески. По SIGTERM
краулер дописывает текущую страницу и сохраняет счётчики прогона, а pm2 по умолчанию
добивает процесс через 1.6 секунды — счётчики теряются, и строка в `scrape_runs`
остаётся «идущей». Такие брошенные строки следующий прогон закрывает сам
(`закрыл незавершённых прогонов: N`), но лучше их не создавать.

Проверить, что режимы встали правильно:

```powershell
pm2 logs bamper-full --lines 5      # в первой строке должно быть «=== full: 12 марок»
```

**Наложения.** Инкремент идёт каждые полчаса, полный проход — ночью, пересечение
неизбежно. Разводится замком `data/scrape.lock` и разным поведением режимов:

- **инкремент** при занятом замке сразу выходит (`уже работает full (pid ...) — выхожу`) —
  ничего не теряется, следующий будет через полчаса;
- **полный проход** ждёт освобождения до 40 минут (`жду до 40 мин`). Выйти он не может:
  это единственный режим, который помечает ушедшие объявления, и его пропуск стоит суток.

Поэтому инкремент стоит на `5,35`, а не на `*/30`: иначе он стартует ровно в те же
минуты, что и полный проход, и тому пришлось бы ждать каждый раз.
Замок от упавшего процесса снимается автоматически — проверяется, жив ли pid.

### Вариант: один процесс вместо трёх задач

```powershell
pm2 start scrape.js --name bamper-scrape -- loop
```

Один живущий процесс: инкремент каждые 30 минут, полный проход когда с прошлого
прошло больше суток (время берётся из `scrape_runs`, поэтому рестарт pm2 не вызывает
лишний полный проход). Минус — полный проход не привязан ко времени суток и сползает
по кругу. Крон-задачи предпочтительнее, если хочется ночного окна.

> Куку `data/clearance.json` все задачи используют общую, а профили и порты Chrome
> у них разные — на случай, если двум одновременно понадобится её обновить.

## Шаг 9. Убедиться, что живёт

Через час:

```powershell
pm2 list                             # bamper-scrape online, restarts 0
pm2 logs bamper-scrape --lines 100   # видны «incremental готово» каждые ~30 мин
npm run status -- --no-verify        # за сутки: новых N, изменений цены M
```

В базе:

```sql
SELECT id, mode, started_at, finished_at - started_at AS duration,
       pages, listings_seen, new_count, changed_count, price_changed, gone_count, errors
  FROM scrapper.scrape_runs ORDER BY id DESC LIMIT 10;
```

## Что делать, если что-то сломалось

| Симптом | Действие |
| --- | --- |
| в логах `ответ 403 ... обновляю клиренс` | норма, если единично: кука обновится сама (нужен доступ к рабочему столу). Если постоянно — увеличить `REQUEST_DELAY_MS` до 3000-4000 |
| `обновить клиренс не вышло` | pm2 работает без рабочего стола: зайти по RDP и выполнить `node tools/clearance.js --refresh` руками |
| `errors` в `scrape_runs` растут | смотреть `pm2 logs`, обычно это сетевые сбои сервера |
| резко упала заполненность полей | сайт поменял вёрстку: `npm test` на фикстурах пройдёт (они старые), поэтому сверять запросом `queries/quality.sql` и обновлять селекторы в `lib/parse.js` |
| много объявлений уехало в `gone` разом | оборвался полный проход. Помечаются только марки, пройденные до конца, но проверить: `npm run status` вернёт в `active` те, чьи страницы живы |
| pm2 в краш-луп | смотреть `pm2 logs bamper-scrape --err`; обработчик `pool.on('error')` уже стоит |
