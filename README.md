# Scrapper — шины с bamper.by

Собирает объявления о шинах с bamper.by (комплекты по 4 шт.), пишет историю цен,
описаний и статусов в Postgres. Цель — база для анализа: какие позиции ходовые,
что влияет на цену (марка, модель, размер, год, остаток протектора, продавец),
и какое объявление выставлено ниже рыночной цены.

Проект отдельный от **Listings** (Kufar) и **Realt** — своя схема БД, свой процесс.
Решения оттуда не переносятся автоматически, но два урока учтены (см. ниже).

---

## Главное, что нужно знать до правок

### 0. Вёрстка сайта сменилась в сентябре 2026 — парсер переписан 29.09.2026

bamper.by переехал на новый шаблон «bamper_new» (Tailwind). Старый Bitrix-разметки
(`#allAds`, `.item-list`, `.price-box`, `.key-features`, `h1.auto-heading`) нет вообще,
скрапер несколько недель отдавал 0 карточек на странице. Что изменилось и как это учтено
в [lib/parse.js](lib/parse.js):

- **Якоря вместо классов.** Осмысленных классов почти нет, парсер держится на ссылках,
  иконках из спрайта и подписях полей: карточка — родитель
  `a.ad-card-carousel-wrapper[href*="/detail_"]`, дата у иконки `#calendar`, город —
  ссылка `/catalog/gorod_*`, доставка — иконка `#truck`, звание продавца — иконка
  `rankIcons.svg#<slug>`. На странице объявления поля идут парами
  `<p class="font-semibold">Подпись</p><p>значение</p>`, цена — `meta[itemprop=price]`.
- **Полный заголовок** («Марка размер, 4 шт., зимние, легковые, б/у, 2022 г.в.») в
  карточке больше не виден: сайт кладёт его в атрибут `title` галереи, с тегами внутри.
  Берём оттуда, теги вырезаем — `parseTitle` работает как раньше.
- **Цены поменялись местами:** крупно теперь цена за комплект, мелко — «р./шт.».
  Справочные $ и ₽ сайт даёт за комплект; в БД `price_usd` по-прежнему за 1 шт., поэтому
  пересчитываем через отношение цен.
- **Счётчика «Найдено N» по разделу больше нет** (в вёрстке закомментирован). Значит,
  сверка на уровне марки из п. 4 (`COMPLETE_MIN_SHARE`) не срабатывает — `totalFound`
  всегда `null`. Защита от неполного обхода остаётся только на уровне прохода
  (`GONE_MAX_SHARE` в [lib/store.js](lib/store.js)). Если сайт вернёт счётчик в виде
  «Найдено объявлений: N», парсер его подхватит сам.
- **Пагинация** — без слова «След.»: ссылки `?PAGEN_1=N`, сортировка `sort=DATE-DESC`
  в них сохраняется. `nextPageUrl(html, currentUrl)` ищет ссылку ровно на страницу N+1;
  за пределами выдачи сайт отдаёт 200 с «Ничего не найдено» и без ссылок.
- **Звания продавца** в списке теперь слагами (`captain`, `colonel-general`…), на
  странице объявления — по-старому `/images/pogony/N.svg`. Соответствие сверено вживую
  по шести званиям (captain 9 … colonel-general 15), таблица в `RANKS`. Появился
  **рейтинг продавца в процентах** («96%») — пишется в `listings.raw.seller_rating_pct`,
  отдельной колонки нет.
- **Снятое объявление по-прежнему 404** — логика `check-status` не тронута.
- **Фикстуры заменены** на снимки новой вёрстки (`fixtures/list-*`, `detail-shop`,
  `detail-private`), `npm test` — 34 проверки. Клиренс Cloudflare при этом не поменялся:
  старая кука отдала 403, новая получена штатно через Chrome.

### 1. Cloudflare: браузер нужен один раз, дальше обычный HTTP

bamper.by закрыт non-interactive challenge Cloudflare. Что проверено вживую:

| Способ | Результат |
| --- | --- |
| curl / fetch **без клиренса**, любые заголовки | 403, «Just a moment…» |
| Playwright обычным запуском (headed и headless) | вечный спиннер: CF видит включённые домены CDP |
| `rebrowser-playwright` (патч против утечки `Runtime.enable`) | тоже не проходит |
| `chrome --headless=new` | не проходит |
| **Chrome решает челлендж сам, мы забираем куку `cf_clearance`** | **работает** |
| **обычный `fetch` Node с этой кукой, Chrome выключен** | **работает: 15/15 страниц подряд** |

Отсюда архитектура из двух частей:

- [lib/chrome.js](lib/chrome.js) — поднимает настоящий Chrome, ждёт, пока тот сам решит
  челлендж, забирает `cf_clearance` и гасит браузер. Подключение к Chrome — напрямую по
  CDP, **без включения доменов**: `Runtime.evaluate` работает и без `Runtime.enable`,
  а именно `Runtime.enable` и палил нас перед CF. Зависимостей нет: CDP — это JSON
  поверх WebSocket, встроенного в Node 22+.
- [lib/session.js](lib/session.js) — вся работа: обычный `fetch` с этой кукой и
  заголовками Chrome. Если сайт вдруг ответил челленджем — кука обновляется через
  Chrome и запрос повторяется.

Практические следствия:

- В куке заявлен срок год (`expires` +365 дней), и полный проход в 318 страниц она
  держит целиком. **Но Cloudflare отзывает её и раньше:** наблюдали 403 через ~40 минут
  после большого прогона. Краулер это переживает сам — поднимает Chrome, берёт новую
  куку и продолжает, — но из этого следует, что **Chrome должен оставаться доступен**,
  а не быть нужен «однажды при установке». Сколько раз за прогон пришлось обновлять
  клиренс, видно в `scrape_runs.note` и в логе: так реальная частота станет известна
  из данных, а не из догадок.
- **Челлендж показывают не всем.** Замерено 29.09.2026: на сервере Chrome открыл
  bamper.by сразу, без «Just a moment», и `cf_clearance` не получил — Cloudflare тому IP
  проверку не показывает. Тогда `mintClearance` печатает, что видит Chrome, убеждается,
  что это настоящая страница bamper.by, и отдаёт сессии те куки, что есть (в
  `clearance.json` будет `noClearance: true`). Обычный `fetch` с такого IP работает и
  без куки. Если проверку начнут показывать — придёт 403, и кука получится штатно.
- Клиренс лежит в `data/clearance.json` и переживает перезапуски процесса.
- Chrome при получении куки стартует **с окном за пределами экрана**
  (`--window-position=-32000,-32000`) — на рабочем столе ничего не мелькает. Именно
  headed, а не headless: headless CF режет. `CHROME_VISIBLE=true` показывает окно для отладки.
- Профиль Chrome удаляется сразу после получения куки. Без флагов из `LEAN_FLAGS`
  Chrome успевает натащить в профиль 260 МБ ML-моделей и кэшей — с ними около 25 МБ,
  и те живут только во время получения куки.
- Клиренс, скорее всего, привязан к IP: получать его нужно на той машине, где будет
  работать краулер. Файл `clearance.json` с чужой машины может не подойти.
- Между запросами пауза 1.8-2.7 с (`REQUEST_DELAY_MS` + джиттер) — вежливость к сайту.

### 2. Идентичность объявления — пара «продавец + артикул», а не число из URL

Глобального id объявления bamper.by не показывает. Последний номер в URL и поле
«Артикул» на карточке — это **внутренний артикул продавца**:

- у продавца `131232` и у продавца `283219` есть объявления с артикулом `22673`
  (разные шины, цены 644 и 632 руб.) — при ключе «только артикул» они схлопывались
  в одну запись и генерировали бесконечные ложные изменения цены;
- артикулы бывают буквенными: `A794083`;
- имена фото это подтверждают: `/upload/shiny/131232/131232_22673_127227687.jpg`.

Поэтому ключ — `external_id = '<seller_id>_<seller_article>'`, он же уникальный
индекс в БД. Разбор — `idsFromUrl()` в [lib/parse.js](lib/parse.js), под это есть тесты.

### 3. Два урока из проекта Listings, уже учтённые

- **Первый снапшот пишется всегда**, даже когда цена не указана (`price_byn = NULL`).
  Иначе появление цены позже не отличить от «ничего не изменилось».
  Цена `0 руб.` с сайта нормализуется в `NULL` — на последних страницах выдачи таких много.
- **`pool.on('error')` в [lib/store.js](lib/store.js) стоит с самого начала.** Без него
  ECONNRESET на простаивающем соединении валит процесс, и pm2 уходит в краш-луп.

### 3а. Исключённые продавцы

Продавец 336639 выставляет цены в десятки тысяч рублей за шину (60+ объявлений,
похоже на российские рубли или ошибку ввода) и портил медианы по редким размерам.
Список таких продавцов — `EXCLUDED_SELLERS` в `.env` (по умолчанию 336639):
краулер их объявления не пишет, а уже записанные строки миграция 006 переводит в
статус `excluded`. Этот статус нигде специально не обрабатывается, и в этом смысл:
модель цен берёт только `active`, калибровка сделок — только `gone`, пометка
ушедших — только `active`. Добавить продавца = дописать id в `.env` и выполнить
такой же `UPDATE`, как в миграции 006.

### 4. «Ушло из выдачи» — вывод, и он защищён двумя порогами

Сайт не говорит, что объявление снято: его просто нет в выдаче. Значит, любой сбой
обхода выглядит как массовая продажа. Так и вышло 21.08.2026: полный проход собрал
4 933 объявления вместо обычных 6 230 и пометил ушедшими 1 319. Назавтра 1 282 из них
вернулись в выдачу — то есть 97% того «ухода» было нашим сбоем. Признак «дошли до
конца раздела» этого не поймал: ссылка «След.» просто кончилась раньше, и разделы
завершились штатно.

Поэтому пометка ушедших проходит через два порога:

- **на уровне марки** ([scrape.js](scrape.js)) — сверка с «Найдено N», которое сайт
  печатает на первой странице. Собрали меньше `COMPLETE_MIN_SHARE` (90%) от обещанного —
  раздел считается непройденным, ушедшие по нему не помечаются;
  **С сентября 2026 сайт этот счётчик не печатает, и порог не срабатывает** (см. п. 0);
- **на уровне прохода** ([lib/store.js](lib/store.js)) — если помечать предстоит больше
  `GONE_MAX_SHARE` (15%) активных объявлений, не помечается ничего, а в `scrape_runs`
  пишется ошибка «неполный обход». Для сравнения, обычная ночь даёт 1-7%.

## Что собирается

Со страницы выдачи (одна страница = 20 карточек, один запрос):

`external_id`, ссылка, заголовок, описание, город, дата объявления, цена за 1 шт.,
цена за комплект, справочные $ и ₽, количество фото, условия доставки,
артикул продавца, **id продавца** (из ссылки), **звание** (иконка `rankIcons.svg#<slug>`)
и **рейтинг продавца в %** (в `raw`),
плюс разобранные из заголовка марка, модель, ширина/профиль/диаметр (и индекс C),
количество, сезон, тип авто, состояние, год выпуска, и остаток протектора из описания.

Со страницы объявления (отдельный запрос, по бюджету): тип продавца (частное лицо /
магазин), город, дата регистрации на сайте, телефон, e-mail, полное описание,
структурированный год выпуска.

Не собирается: рейтинг/отзывы продавца со страницы `/rating/`, сами файлы фото
(только ссылки), объявления не на 4 шт. (`KOLVO`), марки вне выбранных тиров.

## Установка

Зависимостей всего три: `cheerio` (разбор HTML), `pg` (Postgres), `dotenv`.
Браузерных библиотек нет — Chrome дёргается напрямую, поэтому `node_modules` ~10 МБ.

```powershell
npm install
```

Скопировать `.env.example` в `.env` и заполнить. Ключевое:

```
DB_HOST=postgres-ha.local.modsen.app
DB_NAME=lodb
DB_USER=lo_agent
DB_PASSWORD=...
DB_SCHEMA=scrapper

CHROME_PATH=C:/Program Files/Google/Chrome/Application/chrome.exe
BRAND_TIERS=A
KOLVO=4
REQUEST_DELAY_MS=1800
```

### Миграции

Накатываются **вручную**, по порядку номеров, под владельцем схемы `lo_admin`
(приложение работает под `lo_agent`, и он не может выдать права сам себе).

```powershell
# под владельцем — создаёт схему, таблицы, представления и выдаёт GRANT'ы
$env:DB_USER='lo_admin'; $env:DB_PASSWORD='...'; node tools/migrate.js
```

или тем же файлом через psql:

```
psql "host=postgres-ha.local.modsen.app dbname=lodb user=lo_admin" -f migrations/001_scrapper_schema.sql
```

> **База видна только из сети сервера.** С рабочего ноутбука TCP до
> `172.30.0.185:5432` не проходит (проверено: `TcpTestSucceeded: False`) — нужен VPN
> либо запуск с сервера. Поэтому для проверки краула без БД есть `--dry-run`.

## Запуск

```powershell
npm run full           # полный проход по маркам из BRAND_TIERS + пометка ушедших
npm run incremental    # только первые INCREMENTAL_PAGES страниц свежих: новые и смена цены
npm run details        # добор страниц объявлений (продавец, полное описание)
npm run loop           # incremental каждые 30 мин + full раз в сутки
#                        для pm2 есть точки входа без аргументов: jobs/full.js, jobs/incremental.js
npm run status         # суточная сводка + проверка ушедших по прямой ссылке
npm run deals          # позиции ниже рынка: шортлист с сопоставимыми
npm run price-model    # множители модели + проверка на отложенной выборке
npm run notify -- --dry-run   # что улетело бы в Telegram, без отправки
npm run tg-chats       # узнать chat_id получателей (после их /start боту)
npm run reparse        # перепарсить сохранённое по новым правилам разбора
npm run db-check       # доступ к базе: сеть, схема, таблицы, право записи
npm run clearance      # состояние куки Cloudflare + проверка боем (--refresh для обновления)
npm test               # офлайн-тесты парсера на fixtures/, сети не требуют
node tools/quality.js  # заполненность полей после dry-run
```

Полезные флаги:

```powershell
node scrape.js full --dry-run                      # без Postgres, всё в data/dry-run/*.jsonl
node scrape.js full --brands=michelin,toyo         # только эти марки
node scrape.js full --pages=2                      # ограничить страницы (отладка)
node tools/brand-counts.js A B                     # сколько объявлений в тирах
```

### Режимы: что когда

- `incremental` (каждые 30 мин) — ловит новые объявления и изменения цены. Выдача
  отсортирована по свежести, поэтому первых 3 страниц на марку достаточно.
- `full` (раз в сутки) — проходит все страницы, обновляет всё и помечает `gone` то, чего
  больше нет в выдаче. **Помечает только по маркам, пройденным до конца** — если раздел
  оборвался на сетевой ошибке, живые объявления не «похоронятся».
- `details` — бэклог страниц объявлений, `DETAIL_BUDGET` (300) за прогон. На старте
  бэклог равен всему охвату, поэтому полное покрытие продавцами набирается за несколько
  дней. Новые объявления идут вперёд очереди.
Запускать удобнее отдельными задачами по расписанию (pm2 cron), см. [DEPLOY.md](DEPLOY.md).
Наложение полного прохода и инкремента безопасно: в `scrape.js` есть замок
`data/scrape.lock`, второй процесс выходит с сообщением.

- `status` — сводка и проверка: если объявление выпало из выдачи, но страница жива,
  оно возвращается в `active` (иначе статистика «продано» завышена).

## Схема БД (`scrapper`)

Четыре таблицы. Всё, что выводится из данных, в схеме не хранится.

| Таблица | Что в ней |
| --- | --- |
| `listings` | одна строка на объявление: параметры шин, ТЕКУЩАЯ цена, `status`, `first_seen`, `last_checked_at`, `last_changed_at`, `bump_count` |
| `listing_events` | строка на КАЖДОЕ изменение: полный срез меняющихся полей + `reason` |
| `sellers` | продавец: тип, город, звание, на сайте с, телефон, e-mail |
| `scrape_runs` | каждый прогон: страниц, объявлений, новых, изменений, подмен, ошибок, обновлений клиренса |

Проверка без изменений строки в истории не создаёт — обновляется только
`last_checked_at`. Полный проход трогает 6 200 объявлений в сутки, а реальных
изменений порядка 1 500 в месяц: писать строку на каждую проверку значило бы
получить 99% строк «ничего не произошло».

`reason` — единственное, что из значений не выводится. Переход `active -> gone`
выглядит одинаково, а означает разное:

| reason | что произошло |
| --- | --- |
| `new` | первое появление, база отсчёта |
| `changed` | продавец что-то поправил (цена, год, описание) |
| `gone_missing` | пропало из выдачи, страницу не проверяли |
| `gone_confirmed` | сходили по ссылке: 404, реально снято |
| `alive_on_page` | сходили: страница жива, значит это **наш промах**, вернули в active |
| `back_in_search` | снова появилось в выдаче |
| `product_replaced` | продавец переписал объявление под другой товар |

**Подмена товара.** Продавцы переписывают старое объявление под другие шины: ключ
тот же, товар другой. Склеивать истории цен нельзя — аналитика увидит обвал цены
там, где его не было. Поэтому смена марки, размера или количества закрывает строку
статусом `replaced` и создаёт новую с `revision = 2` и своей историей. Правки года,
сезона, состояния, модели подменой не считаются, это обычное изменение.

**Чего в схеме сознательно нет:**

- таблицы `price_changes` — заменена вьюхой `v_price_changes` (`lag` по цене);
- колонки `changed_fields` — что изменилось, даёт вьюха `v_changes` (сравнение с
  предыдущей строкой истории);
- таблицы `listing_status_logs` — статус и причина лежат в самих событиях;
- истории поднятий объявления — продавцы поднимают почти ежедневно, это дало бы
  десятки тысяч строк; держим `bump_count` и `last_bumped_at`.

Представления: `v_active`, `v_gone`, `v_changes` (было/стало по каждому изменению),
`v_price_changes`, `v_market_stats` (медиана и квартили по размеру/сезону/состоянию/сегменту).

**Про «продано»:** сайт не сообщает причину снятия. Мы знаем только `gone` и `reason`
последнего события. Быстрый уход без снижения цены — скорее продажа; долгое висение
и уход — скорее истечение срока. Поэтому в схеме и запросах везде «ушло», а не «продано».

## Аналитика

Готовые запросы в [queries/](queries/):

- `deals.sql` — **ниже рынка**: активные дешевле медианы сопоставимых (тот же размер +
  сезон + состояние + сегмент, минимум 5 сопоставимых) на 20%+;
- `price-factors.sql` — влияние сегмента марки, года, остатка протектора, типа продавца,
  состояния и диаметра на цену;
- `similar.sql` — **история по похожим объявлениям** для одной позиции: сопоставимые активные
  и уже ушедшие с их ценами и сроком до ухода, вердикт «цена против медианы», своя история цены;
- `liquidity.sql` — ходовые позиции: скорость уходов по размерам, оборачиваемость по
  маркам, размер скидки перед уходом, «ушло быстро и без скидки» (материал для
  калибровки детектора) и «висит долго, цену уже снижали».

Осмысленные результаты появятся, когда наберётся история: медиана по размеру — уже
после первого полного прохода, скорость уходов — через 2-4 недели наблюдений.

## Деплой (pm2, тот же сервер, что Listings)

Пошаговый runbook со всеми проверками — в [DEPLOY.md](DEPLOY.md). Коротко:

```powershell
pm2 start scrape.js --name bamper-scrape -- loop
pm2 start check-status.js --name bamper-status --no-autorestart --cron "0 9 * * *"
pm2 save
```

**Проверить при первом деплое:** процессу нужен headed Chrome, то есть интерактивная
сессия пользователя (`parsemgr`). Если pm2 запущен как служба в session 0, Chrome может
не подняться — тогда `[browser] Chrome не открыл порт отладки` или вечный челлендж.
Диагностика на сервере:

```powershell
node scrape.js full --dry-run --brands=vredestein --pages=1
```

Проходит — значит Cloudflare берётся; не проходит — запускать pm2 в сессии
пользователя (Task Scheduler «At log on» + автологин) либо дать процессу рабочий стол.

Как и в Listings, локальная копия и серверная не синхронизируются: файлы копировать
руками и делать `pm2 restart bamper-scrape`.

## Известные ограничения

- **Остаток протектора** берётся из свободного текста описания («остаток 8.5мм»,
  «протектор 2-3 мм»), заполнен примерно у четверти объявлений. Исходная подстрока
  хранится в `tread_raw` — можно проверять и улучшать правила.
- **Модель** разбирается из заголовка после марки; у части объявлений её просто нет.
- **Год выпуска** в заголовке не всегда; страница объявления даёт его чаще (поле «Год выпуска»).
- Одно объявление может встретиться дважды в одном проходе, если его подняли между
  запросами страниц. На данные это не влияет (ключ уникален, изменений не фиксируется),
  разве что в счётчике `listings_seen` прогона.
- Уведомлений (Telegram) пока нет — по договорённости сначала БД и сбор данных.
